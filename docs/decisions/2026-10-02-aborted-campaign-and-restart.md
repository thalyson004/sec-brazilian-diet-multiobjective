# 2026-10-02: Abort and restart after SPEA2 state leakage

The first attempt at the confirmatory matrix was interrupted after 631 batch events: 591 reported the evaluation limit and 40 stopped with errors. Eight additional directories belonged to in-flight work when the scheduler was stopped. The 40 errors all occurred in SPEA2 at initialization after 66 evaluations, when the same worker process moved from a two-objective subset to a three-objective subset. The traceback showed a two-coordinate ideal point being stacked with three-coordinate values in `pymoo`'s SPEA2 survival normalizer.

Root cause: the `pymoo` 0.6.1.6 SPEA2 constructor has a stateful survival object as a default argument. A long-lived worker reused that object across run instances. This could contaminate earlier two-objective SPEA2 runs even when they reached the evaluation limit. The old attempt is therefore **not** part of the confirmatory dataset. All its directories and progress events remain unchanged under ignored local `results/aborted-2026-10-02-shared-spea2-survival/`; no aggregate performance claim uses them.

The runner now constructs a fresh `SPEA2Survival(normalize=True)` for every run. It also explicitly creates fresh survival objects for NSGA-II and SMS-EMOA. A controlled regression test executes all four methods in sequence across two, three, then two objectives in one process and independently checks each saved result. The frozen source inputs, instance selection, objective definitions, seeds, population and evaluation limit are unchanged. This is an implementation correction before a fresh complete campaign, not a retrospective selection of successful attempts.

The corrected campaign starts with an empty `results/runs/` directory. Its per-run `config.json` records the corrected Git revision. Completion requires all 19,200 registered IDs to finish at the evaluation limit and pass independent artifact validation. Any later error will be retained, diagnosed and reported before conclusions are drawn.
